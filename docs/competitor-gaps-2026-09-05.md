# Что есть у похожих проектов и чего не хватает vbuff

Проверка: 5 сентября 2026. Сравнение с текущим рабочим деревом, включая SQLite/DuckDB, полноисторический поиск и менеджер тегов. У конкурентов изучены публичные README и документация, выборочно исходники; приложения не запускались, их производительность и безопасность не аттестованы. Ссылки на ветки изменяемые. Приоритеты ниже — оценка для vbuff, не рейтинг конкурентов.

## Изученные проекты

| Проект | Что полезно изучать |
| --- | --- |
| [Maccy](https://github.com/p0deje/Maccy) | Нативные форматы macOS, маркеры приватности, пропуск следующего копирования |

| [PasteBar](https://github.com/PasteBar/PasteBarApp) | Коллекции, доски, формы, шаблоны, бэкап |

## Где именно это видно в vbuff

- `crates/vbuff-platform/src/clipboard.rs`: реальный захват через arboard, текст либо изображение; неподтверждённые нативные метаданные остаются неизвестными.
- `crates/vbuff-gui/src/state.rs`: доступные действия UI; менеджер тегов подключён, общего backup/restore, редактора групп/профилей и системных сокращений здесь нет.
- `crates/vbuff-gui/src/tag_manager.rs`, `src/history_search.rs`: готовые теги, фильтры и поиск всей истории.
- `crates/vbuff-core/src/workflow/snippets.rs`: SnippetForm, поля, условная видимость, вычисления; не найдено использования в src/ или GUI.
- `crates/vbuff-core/src/workflow/boards.rs`: PinBoard, BoardRouter, ConsumeQueue, CaptureCollector; не найдено подключения этих типов к приложению.
- `crates/vbuff-core/src/intelligence/actions.rs`: ActiveTagger — заготовка предложений тегов, не автоматические правила в работающем UI.
- `crates/vbuff-gui/src/app.rs`: уже есть Compose, объединение текста, Trim, Uppercase, Pretty JSON, Clean Link. Их нельзя записывать в отсутствующие функции.
- `src/main.rs`: действующие CLI-входы. `src/store_owner.rs` и `src/single_instance/` дают основу расширения без второго писателя.
- `docs/tags.md`: отдельные профили/группы и полный переносимый бэкап ещё не реализованы, старый JSON экспорт тегов не содержит.

README содержит устаревшие утверждения, в том числе об отсутствии преобразований текста. Для сравнения приоритет отдавался подключённому коду, а не перечню целевых возможностей.

## Порядок, который я предлагаю

1. **Полный бэкап и проверяемое восстановление.** До изменения профилей обеспечить возврат к рабочей истории, включая теги и файлы.
2. **Профили и группы.** Продолжить уже начатую организацию; чётко отделить профиль, группу, категорию и тег.
3. **Нативный capture.** На macOS — форматы, файлы, маркеры приватности; затем отдельная квалификация Windows. Это увеличит фактически сохраняемые данные, а не только набор отображаемых категорий.
4. **Шаблоны/формы и локальный OCR.** Формы используют существующий core; OCR добавит новый полезный способ поиска.
5. **Правила и CLI.** Реиспользовать единый сервис истории, дать массовые операции и автоматизацию.
6. **Межустройственный обмен, MCP, расширение.** Отдельные opt-in возможности после завершения локальных сценариев.

Пропуск следующего копирования — небольшой самостоятельный шаг. Очередь последовательной вставки также перспективна: ConsumeQueue уже есть, но Compose объединяет записи в один текст и не заменяет управляемую очередь вставки.

PIN-защита коллекции у другого продукта сама по себе не доказывает шифрование базы. Для vbuff шифрование и Touch ID требуют отдельного законченного решения. Также не предлагается синхронизировать живую SQLite/DuckDB простым размещением файла в облачной папке: переносимый архив и запись через приложение — другие механизмы.
