# RFC: единый поисковый стек (тема T1, волна C пункт 1)

Дата: 2026-08-01. База: рабочее дерево ветки `claude/agents-by-items-e16580`.
Статус: **решение не принято**. Документ описывает развилку, не защищает вариант.
Решение принимает владелец проекта.

Входные материалы: [search-grammar-audit.md](search-grammar-audit.md) (карта поверхностей,
12 дефектов), `crates/vbuff-core/src/recall/grammar.rs` (готовый AST + реестр `FacetSpec`,
скомпилирован, покрыт 21 тестом, **не подключён ни к одному живому пути**),
[solid-dry-review-2026-07-26.md](solid-dry-review-2026-07-26.md) §T1.

Номера строк даны на состояние рабочего дерева на момент написания; `vbuff-store/src/lib.rs`
активно правится параллельно, поэтому рядом с каждым номером назван символ, по которому
ссылку можно восстановить после сдвига.

## 1. Развилка за пять минут

Сегодня поиск исполняется дважды: `filter_clips` в GUI работает по массиву клипов в
оперативной памяти (`crates/vbuff-gui/src/projection.rs:23`), `Store::search_page` работает
по SQLite (`crates/vbuff-store/src/lib.rs:1661`), и ни один из них не видит фасетов другого.
Реестр `FacetSpec` уже описывает объединение двух словарей и умеет компилироваться и в
in-memory предикат (`grammar.rs:998`), и в SQL-фрагмент (`grammar.rs:1063`), поэтому вопрос
«одна ли у нас грамматика» уже решён технически, а нерешённым остаётся другой вопрос:
**сколько остаётся исполнителей и, следовательно, что именно пользователь может найти**.

Три варианта: **A** - живым остаётся SQL (`search_page`), GUI ходит в него;
**B** - живым остаётся in-memory, SQL-поиск становится внутренней деталью `vbuff ask`;
**C** - остаются оба, но исполняют один AST из реестра.

Главное, что нужно знать до выбора: варианты различаются **не качеством грамматики**
(её чинит реестр в любом варианте), а тем, **какое подмножество истории вообще
доступно поиску**. Сегодня это 1000 самых свежих клипов, и только вариант A это меняет.

| | A: только SQL | B: только in-memory | C: оба на одном AST |
|---|---|---|---|
| Поиск видит | всю БД | новейшие `min(max_history, 1000)` | как сегодня: GUI 1000, ask вся БД |
| Из 12 дефектов закрывает | 8 (D-1,2,4 после бэкфилла) | 8 (D-1,2,4 без бэкфилла) | 8 (в GUI сразу, в SQL после бэкфилла) |
| Требует бэкфилла | да, §6 целиком | нет | да, но только для SQL-половины |
| Пользователь теряет | sensitive, volatile, опечатки, ранжирование | ничего | ничего |
| Схема БД меняется | да | нет | да (аддитивно) |
| Обратимость | низкая | высокая | высокая для GUI, средняя для store |
| Объём | L (крупный) | S-M | M |

## 2. Факты, которые ограничивают решение

Всё ниже проверено чтением кода в этом дереве; ссылки `файл:строка` - на продакшн-код.

**Ф-1. Поиск в GUI видит не более 1000 клипов, и это жёсткий потолок, а не настройка.**
`GUI_LIMIT = 1000` (`src/main.rs:45`) задаёт стартовый снимок. Через минуту после запуска
поток обслуживания вызывает `refresh_for_memory` (`src/maintenance.rs:27-33`, интервал 60 с,
`maintenance.rs:11`), который перезаписывает `snapshot_limit` (`src/history.rs:349`) значением
`config.max_history.clamp(1, 1_000)` (`src/memory_pressure.rs:28`). При нехватке памяти лимит
дополнительно делится на 2 или на 4 (`crates/vbuff-core/src/reliability.rs:236,242`).
Итог: сколько бы ни стоял `max_history` (допустимо до 100 000, `src/config.rs:552`),
интерактивный поиск никогда не видит больше 1000 новейших клипов.
Константа `MAX_RECALL_INPUT = 10_000` (`crates/vbuff-core/src/recall/search.rs:5`) недостижима.

**Ф-2. До 32 клипов вообще не существуют в SQLite.** `insert_volatile`
(`src/history.rs:64-90`) публикует клип только в оперативную память; `Store::insert` для
memory-only sensitive явно возвращает ошибку (`store/lib.rs:1096-1104`).
Любой SQL-исполнитель их не найдёт никогда.

**Ф-3. Sensitive-клипы физически не индексируются текстом.** При вставке
`item_text` для sensitive пуст (`store/lib.rs:1161-1165`), превью заменено на `[sensitive]`
(`lib.rs:1157`), и `search_page` вдобавок отсекает их предикатом
`json_extract(...,'$.sensitive') = 0` (`lib.rs:1691`). При этом список, кормящий GUI
(`list_with_archive`, `data_lifecycle.rs:406-439`), их **не** отсекает, попап их показывает
замаскированными с двухсекундным «подглядыванием» (`gui/app.rs:2381-2385`, тест
`sensitive_rows_never_render_clip_text`, `app.rs:3511`), а in-memory поиск отказывается
смотреть внутрь текста (`recall/search.rs:167`), но фасетам их не запрещает.
Практически: `app:chrome` сегодня находит sensitive-клип из Chrome, `search_page` - нет.

**Ф-4. Индексов под фасеты нет.** В схеме есть `idx_clips_updated`, частичный
`idx_clips_pinned` (`store/lib.rs:528-529`), `idx_clip_facets_lookup(key,value,clip_id)`
(`lib.rs:641-642`) и индексы simhash/dhash/normalized (`lib.rs:779-791`). Индексов на
`source_app`, `kind`, `created_at` нет. Плюс `search_page` на каждый вызов делает `count()`
(`lib.rs:1674`), а `count()` - это `COUNT(*)` со сканом (`lib.rs:2758-2765`).

**Ф-5. `clip_facets` заполняется только на вставке** (`lib.rs:1245-1251` и `1322-1326`),
удаляется вместе с клипом (`lib.rs:2182`) и при scrub (`lib.rs:906`). Читатель один -
`AND EXISTS` в `search_page` (`lib.rs:1720-1731`). Записываемые ключи: `host`, `color`,
`lang`, `iso_date`, `has_payment_number` (`crates/vbuff-core/src/facets.rs:15-41`).

**Ф-6. Реестр уже маркирует три фасета как неисполнимые в SQL:**
`app` - `Missing(UnnormalizedSource("clips.source_app"))` (`grammar.rs:268`),
`device` - `Missing(UnnormalizedSource("json_extract(...origin_device)"))` (`grammar.rs:306`),
`tag` - `Missing(NotPersisted(...))` (`grammar.rs:292`).
`sql_predicates` возвращает первую же дыру ошибкой и не компилирует запрос частично
(`grammar.rs:1111-1117`) - то есть store может честно отказать вместо тихого нуля.

**Ф-7. `Store::search`/`search_page` не имеют внешних потребителей.** Grep по `src/`,
`vbuff-ipc`, `vbuff-gui` не находит ни одного вызова. Единственный продакшн-путь:
`ask.rs` → `local_similarity_search` → `local_similarity_search_with` (`lib.rs:1916`) →
`search` как лексический пре-фильтр кандидатов, причём при пустом результате берётся
`list` (`lib.rs:1932-1934`), кандидаты фильтруются `ai_allowed && !sensitive`
(`lib.rs:1935`), а SQL-ранжирование затем полностью отбрасывается ради эмбеддингов
(`lib.rs:1972`).

**Ф-8. `vbuff-gui` не зависит от `vbuff-store`** (`crates/vbuff-gui/Cargo.toml`), а
`vbuff-store` зависит от `vbuff-core` (`crates/vbuff-store/Cargo.toml`). Значит реестр
из `vbuff-core` доступен store уже сейчас, а вот GUI не имеет доступа к БД **вообще**:
он читает `AppState::clips` под мьютексом, а наружу шлёт `UiAction` - однонаправленный
enum без ответа (`crates/vbuff-gui/src/state.rs:287`).

**Ф-9. Мьютекс store общий с потоком захвата и обслуживания.** `History` держит
`Arc<Mutex<Store>>` (`src/history.rs:36`); `maintain_idle` берёт лок на весь проход
(`src/history.rs:244-299`), включая бэкфиллы, аудит и FTS-обслуживание, с бюджетом
2 с CPU (`src/maintenance.rs:23`).

**Ф-10. Поиск в GUI пересчитывается не реже раза в секунду.** `filtered()`
(`gui/app.rs:324-332`) вызывается из `update` (`app.rs:493`), а `ctx.request_repaint_after(1s)`
(`app.rs:1006`) гарантирует кадр даже без ввода.

**Ф-11. Прецедент бэкфилла в кодовой базе есть и он медленный.**
`backfill_fingerprints`, `backfill_normalized_fingerprints`, `backfill_embeddings`
вызываются с лимитом 32 за тик (`src/history.rs:255-268`), тик - не чаще 60 с.
10 000 строк при такой скорости - около 5 часов аптайма процесса.

## 3. Производительность на 10 000 клипов

Вопрос сформулирован как «что будет с производительностью», но по фактам Ф-1 и Ф-2
честный ответ другой: **сегодня in-memory поиск на 10 000 клипов не становится медленнее -
он просто перестаёт видеть 9 000 из них.**

- **In-memory (сегодня и вариант B).** Вход ограничен `min(max_history, 1000)` (Ф-1).
  Стоимость кадра: для каждого клипа `primary_text()` обрезается до 4096 символов
  и лоуэркейзится с аллокацией (`recall/search.rs:170-171`); при промахе по подстроке
  включается опечаточный проход, который повторно строит строку на 4096 символов,
  режет её на ≤256 слов, лоуэркейзит каждое и считает расстояние Левенштейна ≤1
  (`search.rs:203-218`). Промах - это типичный случай во время набора, то есть дорогая
  ветка и есть основная. Порядок величины: до ~4 МБ временных аллокаций на кадр при
  1000 клипах, не реже 1 раза в секунду (Ф-10) плюс на каждое нажатие. Рост истории
  до 10 000 этого не меняет.
- **SQL (вариант A).** Текстовый ярус на 10 000 строках всегда уходит в FTS5
  (порог 250 строк, `store/search.rs:4,16`), а это индексный поиск - быстро.
  Но: `count()` на каждый вызов - полный скан (Ф-4); `kind`/`created_at`/`instr(source_app)`
  индексов не имеют - полный скан таблицы, строки которой несут колонку `flavors`;
  `clip_facets` - индексирован и дёшев. Гидрация (`hydrate_clips`, `lib.rs:1845-1857`)
  читает CAS только для выданной страницы, поэтому масштабируется по `limit`, а не по БД.
  Отдельный риск - Ф-9: запрос на каждое нажатие клавиши идёт через мьютекс, который
  поток обслуживания может держать до 2 с.
- **Вывод для решения.** Аргумент «SQL быстрее» верен только для текстового яруса и
  только благодаря FTS. Аргумент «SQL позволяет искать по всей истории» - верен
  безусловно и является настоящим содержанием варианта A.

## 4. Что каждый вариант делает с 12 дефектами аудита

Ключевое наблюдение, которое стоит проверить прежде остальных: **выбор исполнителя
сам по себе не закрывает почти ничего**. Пять дефектов закрывает переход на общий
парсер, независимо от того, сколько исполнителей останется.

| Дефект | A: только SQL | B: только in-memory | C: оба на одном AST |
|---|---|---|---|
| D-1 `app:` не-ASCII | только после материализации + бэкфилла | закрыт сразу (`normalize_lookup` с обеих сторон) | в GUI сразу, в SQL после бэкфилла |
| D-2 `device:` не-ASCII | то же, плюс `json_extract` неиндексируем | закрыт сразу | то же, что D-1 |
| D-3 `tag:` всегда 0 | не закрыт: в SQLite тегов нет вовсе (Ф-6). Но отказ станет явным | не закрыт: `ClipTags` не конструируется в проде | не закрыт, отказ явный в SQL, тихий ноль в GUI |
| D-4 `iso_date:` со временем | закрыт после перезаписи существующих строк | закрыт без бэкфилла (фасеты считаются из живого текста) | закрыт после перезаписи |
| D-5 `has_payment_number` | не закрыт (продуктовое решение) | не закрыт | не закрыт |
| D-6 LIKE vs FTS расходятся | **ухудшение**: расхождение переезжает в попап, результат меняется при переходе истории через 250 строк | обезврежен: SQL перестаёт обслуживать людей напрямую | остаётся, но заперт в `ask` |
| D-7 непересекающиеся словари | закрыт реестром | закрыт реестром | закрыт реестром |
| D-8 незавершённый фасет | закрыт выбором одного `EmptyValue` | то же | то же |
| D-9 кавычки | закрыт общим токенайзером | то же | то же |
| D-10 дубль фасета | закрыт выбором одного `RepeatPolicy` | то же | то же |
| D-11 ложный fail-closed тест | закрыт правкой теста | то же | то же |
| D-12 carve-out против `purge_expired` | не закрыт; в GUI станет заметнее | не закрыт | не закрыт |

Читается так: 5 дефектов (D-7…D-11) закрывает реестр в любом варианте; 3 (D-1, D-2, D-4) -
единая нормализация, и вся разница вариантов в том, платим ли мы за неё бэкфиллом;
2 (D-3, D-5) - продуктовые решения; 2 (D-6, D-12) не являются дефектами грамматики
и переживут любой выбор.

## 5. Варианты

### Вариант A. Живёт SQL: GUI ходит в `search_page`

**Что делаем.** `search_page` принимает `grammar::Query` (реестр доступен store уже
сейчас, Ф-8), `store::search::parse_query` удаляется. Материализуем `app` и `device`
в нормализованном виде, решаем судьбу `tag`. Строим канал «запрос → результат» из
попапа в `src/` (Ф-8: сегодня канал односторонний), с генерацией запроса, чтобы
отбрасывать устаревшие ответы. Near-dup схлопывание, `HistoryScope`, объяснения матча
остаются в GUI поверх страницы результатов.

**Объём: L.** Схема + бэкфилл + новый двунаправленный канал GUI↔store + переписанный
`filter_clips` + решение по потоку/локу (Ф-9). Это не рефакторинг, а смена архитектуры
чтения в попапе.

**Что ломается для пользователя.**
1. Sensitive-клипы исчезают из результатов поиска, оставаясь в общем списке (Ф-3).
   Наблюдаемо так: клип виден в попапе, пользователь набирает `app:chrome`, клип пропадает.
2. Volatile-клипы (до 32, Ф-2) не находятся вообще, включая только что скопированный,
   если он попал в memory-only путь.
3. Исчезает устойчивость к опечаткам (`recall/search.rs:203-218`) - в SQL эквивалента нет.
4. Меняется порядок выдачи: релевантность (позиция подстроки, бонус за начало слова,
   штраф за матч по имени приложения, `search.rs:187-201`) заменяется на
   `pinned, updated_at, seq` (`store/lib.rs:1742`).
5. D-6 становится виден в попапе: одна и та же строка запроса даёт разный результат
   до и после 250 строк истории.

**Что пользователь получает.** Поиск по всей истории вместо 1000 клипов (Ф-1) - и это
единственное, чего не даёт ни один другой вариант. Плюс пагинация уже написана
(`SearchCursor`, `lib.rs:1732-1741`), плюс `host/color/lang/iso_date` становятся
достижимы из GUI.

**Обратимость: низкая.** Схема аддитивна и её можно оставить, но удалённый in-memory
исполнитель и потерянные свойства (опечатки, volatile, sensitive, ранжирование)
придётся восстанавливать. Откат = откат релиза.

**Сигнал, что выбрали неверно.** p95 задержки на нажатие клавиши в попапе выходит за
~16 мс или попап заикается, когда идёт захват/обслуживание (Ф-9); жалобы
«пароль пропал из поиска» и «только что скопированного нет в поиске»; результаты
меняются сами при росте истории.

### Вариант B. Живёт in-memory: SQL-поиск становится внутренним

**Что делаем.** `filter_clips` парсит через `grammar::parse_query` и исполняет
`matches_constraints`. `store::search::parse_query` удаляется; `search_page` остаётся
приватным пре-фильтром `local_similarity_search_with` (Ф-7) и получает текст без
фасетов, либо фасеты через `sql_predicates` для тех ключей, что уже лежат в `clip_facets`.
`host/color/lang/iso_date` в GUI обеспечиваются либо пересчётом `extract_facets`
по клипу (`facets.rs:15-41`: разбор URL плюс регулярка), либо переносом фасетов на `Clip`.

**Объём: S-M.** Ни схемы, ни бэкфилла, ни новых зависимостей крейтов, ни нового канала.

**Что ломается для пользователя.** Ничего из существующего. Но фиксируется потолок:
поиск навсегда ограничен новейшей 1000 (Ф-1). Если пользователь поднимет `max_history`
до 10 000, поиск всё равно не увидит старое, и объяснить это в UI нечем.
Дополнительно: пересчёт `extract_facets` в памяти - это разбор URL и регулярка на клип
на нажатие; при 1000 клипах измеримо, надо мерить до, а не после.

**Обратимость: высокая.** Всё изменение - код, персистентного следа нет.

**Сигнал, что выбрали неверно.** Приходят запросы «искать по всей истории», и
единственный ответ - «поднимите `max_history`», который не работает из-за клампа
(`memory_pressure.rs:28`); растёт CPU на кадр после переноса фасетов в память;
попап и `vbuff ask` продолжают по-разному отвечать на одну строку.

### Вариант C. Оба исполнителя, один AST (в ревью не назван)

**Что делаем.** Один `grammar::parse_query` на обеих поверхностях. GUI исполняет
`matches_constraints` (`grammar.rs:1026`), store исполняет `sql_predicates`
(`grammar.rs:1111`). Дыры в SQL реестр уже описывает (Ф-6), и `sql_predicates`
отказывает целиком вместо частичного применения фильтра - то есть `ask` на `app:Übersicht`
скажет «не умею», а не найдёт литерал `app:Übersicht`.

**Объём: M.** Подключение обеих сторон к реестру, удаление `store::search::parse_query`,
адаптеры `ClipFacetView` для `Clip` (+ `ClipTags`, если `tag:` выживает), и бэкфилл -
но только для тех фасетов, которые решено сделать исполнимыми в SQL.

**Честная оценка: это компромисс, но только при одном условии.**
За: пользователь ничего не теряет; store перестаёт врать (явный отказ вместо тихого
нуля); миграцию можно вести по одному фасету; `ask` получает кавычки и полный словарь;
решение о потолке в 1000 клипов откладывается, не блокируя починку грамматики.
Против: два исполнителя остаются навсегда, и **реестр не гарантирует их одинаковости**.
`normalize_lookup` (`grammar.rs:98-102`) складывает строку по NFKC и круговому
upper/lower в Rust; SQLite сравнивает байты сохранённого значения, и совпадут они
только если значение нормализовано при записи. То есть паритет по-прежнему стоит
бэкфилла, а не одной таблицы. Сюда же: `Contains` в памяти - это `str::contains` по
нормализованной строке, а в SQL - `instr(...)>0` по сохранённой (`grammar.rs:1077-1086`);
текстовый ярус в SQL вообще живёт отдельно от AST (LIKE/FTS, `lib.rs:1697-1718`) и
реестром не описан.

Отсюда условие: C оправдан **только вместе с дифференциальным тестом** - одна фикстура,
один запрос, оба исполнителя, сравнение множеств id для запросов, состоящих из фасетов.
Без такого теста C - худший из трёх, потому что создаёт видимость одной грамматики
поверх двух поведений, и следующий разработчик будет доверять таблице, а не поведению.

**Обратимость: высокая для GUI-половины** (чистый код), **средняя для store-половины**
(бэкфилл аддитивен и идемпотентен, но уже записанное надо будет либо чистить, либо жить с ним).

**Сигнал, что выбрали неверно.** Дифференциальный тест начинают помечать `#[ignore]`
или писать ему разные ожидания на исполнителя; новый фасет приезжает с
`SqlBinding::Missing` и остаётся таким дольше одного релиза; появляются баг-репорты
вида «в попапе находит, в `ask` нет».

## 6. Что требует бэкфилла

Применимо к вариантам A и C; вариант B не требует ничего.

| # | Что | Почему | Объём миграции |
|---|---|---|---|
| 1 | `app` | `clips.source_app` хранится как есть; SQLite складывает регистр только по ASCII (`grammar.rs:268`) | нормализованная колонка или строка `clip_facets` для **каждой** существующей строки |
| 2 | `device` | лежит в `metadata_json.$.lineage.origin_device` (`grammar.rs:306`), неиндексируем и ненормализован | материализация + бэкфилл всех строк |
| 3 | `tag` | не персистится вообще (`grammar.rs:292`), `ClipTags` в проде не конструируется | не бэкфилл, а новая таблица + производитель, либо удаление фасета |
| 4 | `iso_date` | записан verbatim (`facets.rs:32`), читатель лоуэркейзит - это и есть D-4 | перезапись существующих строк `clip_facets` |
| 5 | `host`, `color`, `lang` | записаны через `to_lowercase` (`facets.rs:21,24,29`), а сравнивать будем по `normalize_lookup` | для ASCII совпадает, для не-ASCII нет; перезапись ради точности |
| 6 | `has_payment_number` | если решение «перестать писать» - существующие строки надо удалить | одноразовый DELETE |

Скорость: прецеденты в коде идут по 32 строки за тик обслуживания (Ф-11), то есть
10 000 строк - около 5 часов аптайма. Значит либо поднимаем батч, либо принимаем окно,
в котором фасет отвечает по неполным данным, и тогда он обязан отвечать **заметно**
неполно (через `SchemaGap`, а не тихим нулём).

## 7. Рекомендация

**Рекомендую вариант C** как ближайший шаг, при обязательном условии дифференциального
теста паритета, и **отдельно** вынести вопрос о потолке в 1000 клипов как продуктовый.

Обоснование: развилка «SQL или память» решает не ту задачу, из-за которой открыта тема T1.
Все 12 дефектов, кроме двух, чинятся реестром и единой нормализацией, а не выбором
исполнителя (§4). Вариант C закрывает ту же долю дефектов, что и A, но не забирает у
пользователя ни sensitive-клипы, ни volatile, ни устойчивость к опечаткам, ни
релевантное ранжирование, и не требует строить двунаправленный канал GUI↔store в
том же изменении, где меняется грамматика. Вдобавок C делает следующий шаг дешевле:
после него A сводится к «GUI начинает вызывать уже существующий SQL-исполнитель того
же AST», а B - к «удаляем SQL-половину».

**Главный аргумент против моей рекомендации** (и я считаю его сильным):
C не отвечает на вопрос, который, вероятно, и есть настоящая жалоба пользователя.
Пользователь не говорит «у вас две грамматики», он говорит «я не могу найти то, что
копировал на прошлой неделе». Это Ф-1, и только вариант A её снимает. C оставляет
потолок в 1000 клипов нетронутым, добавляет второй исполнитель в поддержку навсегда
и покупает чистоту кода ценой отложенного продуктового решения. Если владелец считает,
что поиск обязан видеть всю историю, то C - это работа, которую придётся частично
переделать, и тогда честнее идти сразу в A, приняв потери из §5.

Второй аргумент против: C держится на дисциплине (дифференциальный тест), а
дисциплина деградирует. A и B устраняют возможность расхождения структурно.

## 8. Открытые вопросы и кто может ответить

1. **Должен ли поиск видеть всю историю или только «горячее окно»?** Это и есть развилка;
   всё остальное - следствие. Отвечает: владелец продукта. Пока ответа нет, любой выбор
   исполнителя - ставка.
2. **Должны ли sensitive-клипы находиться поиском?** Сегодня: видны в списке
   замаскированными, находятся по фасетам, никогда по тексту (Ф-3). SQL говорит «нет»,
   и store не может ответить иначе - `item_text` для них пуст по замыслу.
   Отвечает: владелец приватности.
3. **Должны ли находиться volatile-клипы?** Они непереносимы в SQLite конструктивно (Ф-2).
   Отвечает: владелец продукта.
4. **`tag:` - удалить или построить?** Сегодня фасет есть в грамматике, автодополнении и
   объяснениях матча, но всегда даёт ноль. Отвечает: владелец продукта; цена постройки -
   таблица + производитель + UI.
5. **`has_payment_number` - вывести в грамматику или перестать писать?** Признак наличия
   номера карты лежит в БД без единого потребителя (D-5). Отвечает: владелец приватности.
6. **`EmptyValue` и `RepeatPolicy` - по одному ответу на каждый.** Сегодня две грамматики
   отвечают по-разному, и реестр честно хранит оба варианта (`grammar.rs:194-215`).
   После решения это правка одной строки таблицы. Отвечает: владелец поискового UX.
7. **Допустим ли SQL-запрос на каждое нажатие клавиши через мьютекс, общий с захватом?**
   (Ф-9, Ф-10.) Это измеримо до принятия решения и должно быть измерено, если
   рассматривается вариант A. Отвечает: владелец задержки захвата.
8. **`MAX_RECALL_INPUT = 10_000` против фактических 1000.** Константа говорит, что кто-то
   закладывал 10 000. Какое число целевое? Отвечает: владелец продукта.
9. **Текстовый ярус вне AST.** Реестр описывает фасеты, но не свободный текст: в памяти это
   подстрока плюс опечатки, в SQL - LIKE или FTS5 с `remove_diacritics 2`. Сводить ли и
   это к одному определению - отдельный вопрос, который ни один из трёх вариантов не решает.
