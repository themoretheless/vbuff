Ревизия читающая: Rust-код этим документом не правился. Выводы сделаны на

## 1. Карта домена

### 1.1. Где детектируются секреты

Один модуль: `crates/vbuff-core/src/secret.rs`.

`detect_secrets(&str) -> Vec<SecretFinding>` — единственный детектор во всём
воркспейсе. Возвращает не более одной находки на `SecretKind`, никогда не
удерживает совпавший текст. Восемь классов, в порядке убывания тяжести (порядок
объявления `SecretKind` — тай-брейк при равной уверенности):

| `SecretKind` | Правило | Уверенность |
| --- | --- | --- |
| `PrivateKey` | подстроки `-----BEGIN ` и `PRIVATE KEY-----` во всём тексте | 1.00 |
| `CloudCredential` | токен ровно 20 байт, префикс `AKIA`/`ASIA`, дальше `[A-Z0-9]` | 0.98 |
| `AccessToken` | префикс из списка `ghp_`, `gho_`, `github_pat_`, `glpat-`, `sk_live_` + ≥16 байт хвоста | 0.97 |
| `OneTimePassword` | контекстное слово + цифровой прогон 4..=8, **или** весь текст — цифровой прогон 4..=8 | 0.96 / 0.90 |
| `JsonWebToken` | три base64url-сегмента, header начинается с `eyJ`, payload ≥8, signature ≥16 | 0.95 |
| `RecoveryCode` | контекст `recovery`/`backup code` + токен 8..=64 алфанум/дефис с цифрой и буквой | 0.94 |
| `PaymentCard` | 13..=19 цифр в токене, проходящих Luhn | 0.90 |
| `HighEntropy` | токен 24..=256 ASCII, **не** структурный локатор, ≥3 из 4 классов символов, Шеннон ≥ 3.8 | 0.72 |

Токенизация для всех правил кроме `PrivateKey` и `OneTimePassword` — разбиение
по ASCII-пробелам и по `,;()[]{}<>"'`. OTP ищет цифровые прогоны напрямую,
поэтому пунктуация его не прячет.

Второй проход по локаторам (`secret.rs:159-171`): если токен содержит `://`,
содержит `\` или начинается с `/` (`is_structured_locator`), он дополнительно
режется по `/?&=#\` и каждая часть прогоняется через `scan_token` ещё раз.
Энтропийный детектор при этом на самом локаторе воздерживается
(`probable_high_entropy`, `secret.rs:345-347`), структурные — нет.

### 1.2. Пороги

Два именованных порога, оба в `secret.rs`:

- `min_actionable_confidence(kind)` — пол для решений **на захвате**:
  `HighEntropy` → 0.70, все остальные → 0.90. Ошибка стоит замаскированного
  клипа с коротким TTL.
- `MIN_RECLASSIFY_CONFIDENCE = 0.90` — пол для **ретроактивной**
  переклассификации уже сохранённого клипа. Сознательно не зависит от класса и
  сознательно строже: он отсекает ровно `HighEntropy` (0.72). Направление
  асимметрии закреплено тестами `reclassification_floor_is_never_looser_than_capture`
  (в `secret.rs` и повторно в `vbuff-store`).

До правок агентов порогов было три: `secret_threshold` в `capture/policy.rs`
(0.7/0.9), литерал `>= 0.9` в `Store::clawback_sensitive` и отсутствие порога
(`!detect_secrets(..).is_empty()`) в `plugin/migration.rs` и в
`recall/memory.rs`. Сейчас все четыре точки спрашивают именованный пол.

### 1.3. Тракт: захват → хранение → показ

```
ArboardClipboard::read()            crates/vbuff-platform/src/clipboard.rs
  → CapturedClipboard{4 поля evidence, все Unknown}
      ↓
CapturePolicy::decide()             crates/vbuff-core/src/capture/policy.rs:284
  порядок гейтов: Empty → coherence → self_write → intent(PRIMARY)
                  → concealment → NoRealizedFlavor → provenance/rules
                  → excluded_apps → source rules → whitespace
                  → actionable_findings()
  выдаёт: sensitive, sync_eligible, ai_allowed, memory_only,
          expires_after, sensitivity_reason
      ↓
src/capture.rs:build_clip()  →  ClipMeta
      ↓
memory_only ? History::insert_volatile()  : History::insert() → Store::insert()
              (RAM, MAX_VOLATILE_CLIPS)     tighten_sensitive + scrub колонок
      ↓
чтение: все SQL-выборки фильтруют sensitive = 0
показ:  masked_preview_label() → SensitivityReason::watermark()
выдача: PasteWriter::copy() требует доказанного исключения из истории ОС
```

Из `ClipMeta` **не** сохраняются ни `ConcealmentSignal`, ни
`GenerationCoherence`, ни `SelectionIntent` — эти три сигнала живут только
внутри одного решения гейта. Сохраняется `provenance_confidence`.

## 3. Остатки fail-open

Критерий: отсутствие информации (`None`, `Unknown`, пустое, дефолт) приводит к
решению «безопасно», а не «неизвестно». Волна A закрыла concealment и
provenance; волна B3 закрыла `coherent_generation` и `primary_intended`.
Остались следующие.

### F1. `StoredMetadata.sync_eligible: Option<bool>` → `unwrap_or(true)`

`crates/vbuff-store/src/lib.rs` (`StoredMetadata::apply_to`). Единственное
приватное поле в этой структуре, которое при отсутствии в JSON становится
разрешением, а не запретом: `provenance_confidence` → `Unknown`, `ai_allowed`
→ `false`, `sensitive` → `false`, и только `sync_eligible` → `true`.

**Достижимость: высокая, не зависит от бэкенда.** Миграция v1→v2
(`lib.rs:395`) выполняет `ALTER TABLE clips ADD COLUMN metadata_json TEXT NOT
NULL DEFAULT '{}'`, то есть каждая строка, созданная до появления приватных
полей, имеет ровно `{}` и десериализуется в «синхронизировать можно».
Смягчающее обстоятельство: продакшн-путей синхронизации сейчас нет вообще
(`vbuff-sync` не подключён в `src/`), так что утечка латентна — но она
сработает в момент включения sync, а не в момент правки store.

### F2. `COALESCE(json_extract(metadata_json, '$.sensitive'), 0)`

18 SQL-мест в `vbuff-store/src/lib.rs`. NULL (невалидный JSON, отсутствующее
поле) читается как «не sensitive».

**Достижимость: низкая.** `metadata_json` всегда пишется через `serde_json`, а
гидратация строки (`row_to_clip` → `serde_json::from_str::<StoredMetadata>`)
на битом JSON вернёт ошибку и уронит весь запрос — то есть fail-open в SQL
перекрыт fail-closed на уровне выше. Исключения — два места, где COALESCE
единственный гейт и гидратации не следует: свип при открытии (`lib.rs:765-775`)
и выборка кандидатов клоубэка (`lib.rs:1985`). Там строка с испорченными
метаданными просто не будет скрабнута. Реально достижимо только при
постороннем вмешательстве в БД.

### F3. `Flavor::as_text()` → `None` молча исключает флейвор из детекции

`vbuff-types/src/lib.rs:550` возвращает `None` для не-UTF-8 и для
`Body::Spilled`. Все детекторы фильтруют через `filter_map(Flavor::as_text)`
(`policy.rs:447`), поэтому такой флейвор не сканируется вообще, но при этом
хранится.

**Достижимость: нулевая с arboard, высокая с будущим нативным бэкендом.**
`arboard::get_text()` отдаёт Rust `String` (всегда валидный UTF-8), а тела на
момент гейта всегда `Inline`. Нативный бэкенд, сохраняющий сырые байты
флейвора, немедленно это откроет: Windows `CF_UNICODETEXT` — UTF-16LE, X11
`text/plain;charset=utf-16` — тоже. Для такого флейвора `is_text()` вернёт
`true` (проверяется MIME-эссенция `text/plain`), а `as_text()` — `None`, то
есть секрет в нём невидим гейту. Побочно: `has_text` тоже станет `false`, и
whitespace-проверка отключится.

### F4. `FlavorRealization::default() == Realized` и сканирование только реализованных

`vbuff-types/src/lib.rs:432-438`. Флейвор, десериализованный без поля,
объявляет себя полностью реализованным. Обратно: `Truncated`/`Deferred`
флейвор в гейте пропускается (`policy.rs:446`), хотя проверка
`NoRealizedFlavor` требует лишь **хотя бы одного** реализованного — то есть
частично реализованный флейвор может попасть в хранилище несканированным.

**Достижимость: нулевая сегодня.** Ни один продакшн-путь не эмитит ничего
кроме `Realized` (`Truncated` встречается только в `format_fidelity.rs`,
`Deferred` только читается в `coalesce.rs`). Открывается вместе с нативным
бэкендом, умеющим отложенный рендер флейвора. Порядок в `src/capture.rs`
сейчас защищает shed-путь: `policy.decide()` вызывается до
`shed_to_text_preview`, поэтому усечение до превью не может снять уже
проставленную метку.

### F5. Клоубэк видит меньше текста, чем гейт захвата

`clawback_sensitive` (`lib.rs:2020`) сканирует колонку `item_text`, которая
строится `searchable_projection` из `clip.primary_text()` — **первого**
`text/*` флейвора — плюс `source_app` и метка kind, всё усечённое до 1 МиБ.
Гейт захвата сканирует **каждый** реализованный текстовый флейвор (закреплено
тестом `every_text_flavor_is_scanned_and_non_text_prevents_whitespace_drop`).

**Достижимость: низкая с arboard, высокая с мультифлейворным бэкендом.**
arboard отдаёт ровно один текстовый флейвор. Как только появится нативный
бэкенд, секрет во втором текстовом флейворе (например `text/x-token` рядом с
`text/plain`) будет навсегда недоступен переклассификации, хотя свежая копия
того же содержимого была бы замаскирована. То же для секрета за границей 1 МиБ.

### F6. `ClipAccessContext.concealed: bool` — двузначное поле для трёхзначного сигнала

`vbuff-ipc/src/integration/access.rs:28`. Везде в тракте concealment — это
`ConcealmentSignal{Clear, Concealed, Unknown}`, здесь — `bool`. Честного
значения для него не существует: `ConcealmentSignal` вообще не сохраняется в
`ClipMeta`, поэтому у любого будущего конструктора нет источника.

**Достижимость: нулевая сегодня.** У `ClipAccessContext` нет ни одного
продакшн-конструктора — только тест `access.rs:383`. Это заряженная мина для
подключения MCP/IPC: подключающему придётся отобразить «мы никогда не
записывали concealment» в `false`.

### F7. `export_clips_json` V2/V3 не имеет гейта на sensitive

`vbuff-store/src/data_lifecycle.rs:323-332` отказывает только V1, и только
потому что V1 не умеет нести поля политики. V2/V3 сериализуют клип целиком,
включая плейнтекст флейворов sensitive-клипа, в JSON-файл.

**Достижимость: нулевая сегодня.** `Store::export_json` не вызывается ни из
`src/`, ни из `vbuff-gui`. Латентно до появления кнопки «экспортировать
историю».

### F8. `self_write` при отравленном мьютексе → `false`

`src/capture.rs:394-400`. Отравление мьютекса реестра самозаписей приводит к
`false`, то есть приложение перезахватывает собственную вставку.

**Достижимость: только после паники в другом потоке.** Ущерб ограничен:
детекция прогоняется по тем же байтам заново, поэтому sensitive-клип остаётся
sensitive; получается дубль строки, а не рассекречивание.

### F9. Третий и четвёртый каналы заявлений о возможностях бэкенда

Ревизия насчитала два канала evidence; их было четыре, и волна B3 убрала
второй (`ClipboardBackend::evidence()` и `BackendEvidence` удалены целиком,
единственным каналом остались поля `CapturedClipboard`). Остались:

- `SecurityPosture::detect(strict_mode, core_dumps_blocked, ptrace_blocked)`
  (`vbuff-platform/src/capabilities.rs:48`) — не принимает бэкенд вообще и
  зашивает `clipboard_privacy_markers: Unavailable`,
  `clipboard_provenance: Unavailable`, `foreground_identity:
  Unavailable|Degraded` литералами.
- `DeliveryCapabilities.sensitive_copy: false` литералом в `src/app.rs:230`.

Оба сегодня fail-closed и совпадают с реальностью arboard, но это утверждения
о бэкенде, сделанные без обращения к бэкенду. При появлении нативного бэкенда
`doctor`, шапка GUI и фактическое поведение гейта разойдутся именно здесь.

## 4. Дефекты

Ошибки, а не компромиссы.

**D1. Ветка `denied_source_count` недостижима.** `privacy_posture_input`
(`src/main.rs:225-238`) обнуляет вклад source-правил в приватный балл, если
`foreground_identity != Active`. Ни одна ветка `SecurityPosture::detect`
(`capabilities.rs:51-65`) не выдаёт `Active` — только `Unavailable` (Wayland)
или `Degraded`. То есть исключённые приложения и `Skip`-правила никогда не
попадают в балл. Направление безопасное, но это мёртвый код, выдающий себя за
работающий.

**D2. Литералы в `privacy_posture_input`.** `strict_local_only: false`,
`sensitive_memory_only: false`, `telemetry_enabled: false`, `sync_enabled:
false` (`src/main.rs:241-244`) — константы, не связанные ни с конфигом, ни с
поведением. `sensitive_memory_only: false` при этом фактически неверно: гейт
действительно уводит `PrivateKey`, `RecoveryCode` и `OneTimePassword` в
volatile-полосу (`handling_for_secret(..).memory_only`). Балл занижается — то
есть ошибка в безопасную сторону, но это устаревший литерал, а не решение.

**D3. `sync_eligible.unwrap_or(true)`** — см. F1. Единственное поле политики,
выбивающееся из fail-closed соглашения остальных.

**D4. Клоубэк сканирует более узкий вход, чем гейт** — см. F5.

**D5. `ClipAccessContext.concealed` невозможно заполнить честно** — см. F6.

**D6. Экспорт V2/V3 без гейта на sensitive** — см. F7.

**D7. Энтропийный детектор слеп к hex-секретам.** `probable_high_entropy`
(`secret.rs`) требует ≥3 из 4 классов символов. Проверено расчётом по той же
формуле, что в коде: 64-символьный hex-ключ вида
`a3f5c9e2b7d1408a…` имеет энтропию 3.93 (выше порога 3.8), но всего 2 класса
символов — детектор не срабатывает **никогда**. То же для любого
lowercase-alnum секрета: base32-строки, hex-дайджесты, часть форматов API-ключей.
Окно длины 24..=256 дополнительно исключает короткие пароли.

**D8. Список префиксов токенов из пяти элементов и токенизация без `=`.**
`is_access_token` знает только `ghp_`, `gho_`, `github_pat_`, `glpat-`,
`sk_live_`; нет `sk-` (OpenAI), `xox*` (Slack), `AIza` (Google), `npm_`.
Дополнительно: разделители токенизации — пробелы и `,;()[]{}<>"'`, среди них
нет `=`, а `is_access_token` проверяет именно **начало** токена. Поэтому в
строке `.env` вида `GITHUB_TOKEN=ghp_…` весь фрагмент — один токен, префикс не
в начале, структурный детектор молчит. JSON вида `"token":"ghp_…"`
детектируется, потому что кавычка — разделитель.

Новый проход по частям локатора это **не** покрывает: он включается только для
токена, содержащего `://`, содержащего `\` или начинающегося с `/`
(`is_structured_locator`), а строка `.env` не подходит ни под одно из трёх,
хотя разделитель `=` в списке проходa есть.

Смягчение (проверено расчётом): для реалистичного PAT такая строка всё равно
ловится энтропийным детектором (`GITHUB_TOKEN=ghp_A1b2C3d4…` → 4 класса,
энтропия 5.09). Но ловится как `PossibleSecret` с TTL 2 мин вместо
`AccessToken` с 5 мин — и, что важнее, с уверенностью 0.72, то есть **ниже**
порога переклассификации: в старой истории такой секрет клоубэк не найдёт
никогда (см. R2). Вырожденный случай (`TOKEN=ghp_aaaa…`, энтропия 2.03) не
ловится вообще.

**D9. Латентная паника в `shannon_entropy`.** Функция индексирует
`[u16; 128]` сырым байтом. Её спасает только ранний возврат
`!token.is_ascii()` в единственном вызывающем (`probable_high_entropy`).
Второй вызывающий без такой проверки даст выход за границы.

## 5. Требует решения

**R1. Объединённое OTP-правило теперь применяется ретроактивно, разрушительно
и без отката.**

Унификация двух эвристик выполнена как объединение: маркеры стали
`["otp", "one-time", "verification", "verify", "code"]`, длина цифрового
прогона `4..=8`, прогон ищется где угодно в тексте. На захвате это ровно то
поведение, что уже отгружалось (`is_probable_otp` имел тот же маркер `code` и
тот же диапазон) — регрессии нет. Новое здесь другое: раньше
`Store::clawback_sensitive` пользовался **узким** детектором (маркеры
`otp|one-time|verification code|security code`, цельный токен из 6..=8 цифр), а
теперь спрашивает то же самое правило. Порог 0.96 ≥ `MIN_RECLASSIFY_CONFIDENCE`.

Клоубэк запускается на каждом тике простоя (`src/history.rs:253` внутри
`History::maintain_idle`) и разрушителен: `item_text` обнуляется, `preview`
становится `[sensitive]`, все проекции сходства NULL-ятся, фасеты и эмбеддинги
удаляются, строке навязывается expiry — после которого `purge_expired` её
удалит. Отката нет.

Под правило попадает обычный текст: `error code 1024`, `discount code SAVE20
valid until 2026` (их собственный характеризационный тест
`merged_rule_inherits_the_capture_gates_marker_false_positive`), любой фрагмент
кода со словом «code» и четырёхзначным числом. Для существующих историй это
новое, видимое пользователем поведение.

Варианты: (а) оставить широкое правило только на захвате, а клоубэку дать
узкий контекстный список; (б) требовать для клоубэка якорь «весь текст —
цифровой прогон»; (в) сделать переклассификацию неразрушительной (помечать
sensitive, не стирая `item_text`), тогда она обратима.

**R2. `MIN_RECLASSIFY_CONFIDENCE` исключает ровно тот класс, который чаще
всего лежит в старой истории.** Константа кинд-независима и равна структурному
полу, то есть отсекает единственный класс ниже него — `HighEntropy` (0.72).
Это задокументировано и закреплено тестом, но следствие: строка легаси-истории,
которая **является** высокоэнтропийным секретом, не будет переклассифицирована
никогда, хотя свежая копия того же содержимого маскируется. В сочетании с F1
(`sync_eligible` легаси-строк = `true`) это конкретный сценарий: старый
API-ключ в истории остаётся sync-eligible и после клоубэка.

**R3. Тумблер `detect_secrets` не выключает OTP.** `actionable_findings`
(`policy.rs:450-452`) при `detect_secrets = false` оставляет находки
`OneTimePassword`. Поведение сохранено из прежнего кода (там `is_probable_otp`
считался вне тумблера) и обосновано в doc-комментарии, но ключ конфига
называется `detect_secrets`, и пользователь, выключивший «детекцию секретов»,
получает не то, что прочёл.

**R4. `SelectionIntent::Unknown` отказывает PRIMARY во всех режимах, включая
`Allow`.** Решение сознательное и сегодня ничего не роняет (ни один бэкенд не
сообщает PRIMARY). Следствие: у `UnknownEvidencePolicy::Allow` больше нет
власти над intent, поэтому будущий X11/Wayland-бэкенд не сможет отгрузить
режим «всё равно захватывать PRIMARY» без правки кода гейта.

**R5. Каналы заявлений о возможностях бэкенда** — см. F9. Второй канал убран;
третий (`SecurityPosture`) и четвёртый (`DeliveryCapabilities.sensitive_copy`)
остались и по-прежнему говорят за бэкенд, не спрашивая его.

**R6. Воздержание энтропии на локаторах закрыло удаление ссылок, но
компенсация неполна.** Волна B3 нашла и исправила серьёзный дефект, которого
ревизия не называла: энтропийный детектор срабатывал на обычной ссылке и на
обычном пути Windows (проверено расчётом по формуле из кода:
`https://example.com/blog/post?utm_source=Newsletter&id=8fA2` — 4 класса,
энтропия 4.57; `C:\Users\denis\Documents\Projects\report-2026-Q3.xlsx` — 4
класса, 4.48), то есть скопированная ссылка получала маску, запрет sync/AI и
TTL 2 минуты, после чего `purge_expired` её удалял. Исправление:
`probable_high_entropy` воздерживается на структурных локаторах, а сам локатор
дорезается по `/?&=#\` и части сканируются отдельно, чтобы настоящий секрет в
ссылке не потерялся.

Проверено, что компенсация работает на реальных формах (расчёт по той же
формуле): `postgres://user:hunter2@db.example.com:5432/mydb`,
`mongodb+srv://admin:S3cr3tP4ss@cluster0…`,
`smb://DOMAIN\user:P@ssw0rd123!@fileserver/share`,
`https://hooks.slack.com/services/…/aB3xK9mQ7pL2vN5rT8wZ1yC4` — все
по-прежнему дают `HighEntropy`, потому что userinfo-часть или последний
сегмент сами по себе ≥24 символов.

**Остаточный класс.** Порог длины 24 применяется к **каждой части**
по отдельности, поэтому высокоэнтропийный блоб, который (а) начинается с `/`
или содержит `\` и (б) разбивается своими же `/` на фрагменты короче 24,
теряется целиком — раньше он ловился как единый токен. Проверено:
`/aB3xK9mQ7pL2vN5r/T8wZ1yC4dE6fG8` (энтропия 4.88, до правки — находка; после
— части 16 и 14 символов, находки нет) и `x7Kp/9Lm2Nq4Rs6T\u8Vw0Xy2Zb4Cd6`
(4.76 → части 4/11/14, находки нет). Doc-comment у `is_structured_locator`
оговаривает случай «base64 может содержать `/`, но редко начинается с него»;
он не оговаривает комбинацию «начинается с `/` **и** содержит `/` внутри»,
а именно она обходит второй проход. Класс узкий и надуманный, реалистичный
AWS-ключ (`wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY`) не задет — но это
единственное место во всей волне, где детект стал уже, а не шире, и это стоит
зафиксировать как осознанный размен, а не считать, что второй проход
компенсирует всё.

## 6. Что проверено и подтверждено закрытым

- **Sensitive-кламп в одном месте.** `tighten_sensitive` + трейт
  `SensitiveRecord` с двумя реализациями (`ClipMeta`, `StoredMetadata`) — это
  одна политика с двумя носителями, а не две копии. Третьей копии нет:
  `sanitize_import_privacy` (`data_lifecycle.rs:1228-1233`) ставит
  `sync_eligible`/`ai_allowed` в `false` для **любого** импорта (более строгое,
  отдельное правило) и вызывает тот же `tighten_sensitive` при находке. Новый
  код копий не завёл.
- **Scrub-SQL в одном месте.** `SENSITIVE_SCRUB_SET` — единственное
  определение, используется свипом при открытии и клоубэком; тест
  (`lib.rs:3233`) проверяет, что каждая колонка входит в константу.
  Дословных копий списка колонок в коде нет.
- **`SecretHandling.{mask, sync_allowed}` удалены.** `SecretMask` вместе с
  вариантами `LastFour`/`Grouped` убран из `trust/secrets.rs` и из реэкспорта
  `trust/mod.rs`. Это была ложная ручка в обе стороны: `sync_allowed`
  константно `false` во всех восьми классах, а `mask` не реализован нигде —
  шипящая маска приходит из `SensitivityReason::watermark()` в `vbuff-types` и
  всегда полная. Читателей вне собственных тестов у обоих полей не было.
- **Fail-open булевы в `CapturedClipboard::default()` закрыты.**
  `coherent_generation: true` → `GenerationCoherence::Unknown`,
  `primary_intended: true` → `SelectionIntent::Unknown`; ручной `impl Default`
  заменён на `#[derive(Default)]`, так что забытое поле теперь не заявляет
  ничего вместо того чтобы заявлять доказательство. `SelectionSource::default()
  == Clipboard`, так что derive не изменил источник выборки.
- **Второй канал evidence удалён.** `BackendEvidence` и
  `ClipboardBackend::evidence()` убраны; единственный потребитель
  (`src/capture.rs`) теперь судит о деградации source-приватности по
  `provenance_confidence` реального чтения. Побочно закрыто: `evidence().concealment`
  не имел ни одного читателя вообще.
- **Детект секретов не ослаб нигде, кроме одного узкого класса (R6).**
  Проверено по классам:
  - OTP: новое правило — надмножество обеих старых. Маркеры старого детектора
    поглощены (`verification code` ⊂ `verification`, `security code` ⊂ `code`),
    маркеры старого гейта поглощены (`passcode` ⊂ `code`), диапазон расширен с
    6..=8 до 4..=8, поиск переведён с токенов на цифровые прогоны (ловит
    `code:123456`). Правило «весь текст — цифры 4..=8» сохранено дословно.
  - Структурные детекторы не тронуты и получили **дополнительный** проход по
    частям локатора, то есть стали шире: секрет в query-строке ссылки раньше
    не детектировался вообще (весь URL — один токен, префикс `ghp_` не в
    начале), теперь детектируется.
  - Энтропийный детектор сужен ровно на структурных локаторах — единственное
    сужение во всей волне, разобрано в R6.
  - Пороги 0.7/0.9 перенесены в `min_actionable_confidence` как 0.70/0.90 без
    изменения значений.
  - `text_requires_sensitive_handling` (путь правки текста в GUI) стал тонким
    алиасом того же предиката — старая дизъюнкция `is_probable_otp || …`
    покрыта, потому что OTP теперь внутри `detect_secrets`.
  - `recall::query_looks_sensitive` потеряла инлайновую копию правила
    «4..=8 цифр»; замена (`text_contains_actionable_secret`) её включает, а
    прежний нулевой пол не ослаблен: единственный класс ниже 0.90 —
    `HighEntropy` с 0.72 при поле 0.70.
  - `plugin::MigrationPreflight` перешла с нулевого пола на пол захвата:
    отличие только для гипотетического будущего детектора со слабой
    уверенностью; сегодняшние восемь классов все выше своих полов (закреплено
    `every_detector_clears_its_own_actionable_floor`).
  - Клоубэк: правило OTP расширилось (см. R1), остальные классы без изменений.
- **Пороги ужесточились там, где раньше расходились.** TTL для OTP был 90 с в
  гейте (`otp_ttl`, недостижимый из конфига) и 60 с в таблице
  `handling_for_secret`; теперь таблица единственная, применяется 60 с. TTL
  клипа теперь **минимум** по всем находкам, а не TTL победившей; `memory_only`
  — дизъюнкция по всем находкам, а не свойство победившей. Пример из их же
  теста: `ghp_…`-токен, который одновременно высокоэнтропийный, получает 2 мин
  (энтропия) вместо 5 мин (токен).

## 7. Уточнение к записи о закрытии волны B3

Запись в `solid-dry-review-2026-07-26.md` (пункт 3 волны B) утверждает, что из-за
расхождения списков маркеров `"Your one-time password is 483920"`
«захватывался как НЕ секретный — синхронизировался, был доступен ИИ, без TTL».
Перепроверено по коду `f8b2fbd` (`policy.rs:354-401` до правки): это верно
**только при `detect_secrets = false`**.

При значении по умолчанию (`detect_secrets: true`) ветка `secret_finding`
вызывала тот самый `detect_secrets`, у которого маркер `"one-time"` был, и
находка `OneTimePassword` 0.96 проходила порог 0.9; `sensitivity_reason`
становился `OneTimePassword`, TTL — 60 с из `handling_for_secret`,
`memory_only` — `true`. То есть в дефолтной конфигурации утечки не было: она
открывалась ровно тогда, когда пользователь выключал детекцию секретов, потому
что тумблер гасил единственную ветку, знавшую маркер `"one-time"`, а
`is_probable_otp` его не знал. Правка это закрывает по обеим причинам сразу
(объединённый список маркеров плюс вывод OTP из-под тумблера в
`actionable_findings`), но масштаб в записи завышен.

Зеркальное утверждение той же записи — «голый шестизначный код маскировался
гейтом, но был невидим для реклассификации в store» — подтверждается
полностью и достижимо в конфигурации по умолчанию: `is_probable_otp("123456")`
давал `true`, а `detect_secrets("123456")` без контекстного слова не давал
ничего, поэтому `clawback_sensitive` такую строку не находил никогда.
